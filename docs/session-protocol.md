# Local sessions: setup and protocol

[VISION.md](../VISION.md) is authoritative. Pi owns execution/tools/context/extensions/history. PiSpark hosts the local runtime, commands and observation; the browser is not its owner. See [runtime details and limitations](session-runtime.md).

## Setup

There is no configuration file. Start the server (`npm run dev` or `npm start`) and PiSpark uses its data folder: `PISPARK_HOME`, or `~/.pispark` when that isn't set. A leading `~` is expanded. On first start it creates the folder layout and a **Default** agent with Pi's built-in tools (`read, bash, edit, write, grep, find, ls`), so a new session can work with files right away. Sign in to a provider under **Providers & models** and choose a model.

```text
<data folder>/
├── pispark.lock         one server per data folder
├── agents/<id>/       agent.json + instructions/, skills/, prompts/, extensions/
├── apps/<agent id>/   the working folder of an app agent that names none
├── sessions/<id>/          session.json, Pi's transcript, files/ (attachments), an optional agent/ layer (deleting a session removes it)
├── providers/           Pi's auth.json, settings.json and model files
└── logs/
```

For development, point `PISPARK_HOME` at a separate folder in the repository's ignored `.env` (for example `PISPARK_HOME=~/.pispark-dev`) so your everyday data is never touched. A second server on the same data folder refuses to start; a lock left by a process that is gone is replaced.

Ask chooses the **working folder** (any existing folder on the backend host; defaults to the user's home, with recent folders offered), the **agent** (Default when not chosen) and the **model**. A [project agent](agents.md#project-agents) works in its own folder, which Ask shows locked. Folder paths are backend-host paths. Native tools run with the server's OS permissions and are cwd-bound, **not filesystem-confined**. Agents can enable tools, extensions and commands; see [agents](agents.md).

`HOST` accepts only `127.0.0.1` or `::1`. This is a **trusted single-user local service**, not an authenticated remote deployment. Do not forward its port, put it behind a public proxy, or share it with untrusted local users. PiSpark depends on nothing installed on the machine beyond Node: the Pi SDK is an npm dependency, and terminal Pi and `~/.pi` are never read. Styles, remote/multi-user hosting and a marketplace are not built.

### Required runtime security gate

All production startup fails conservatively before native provider auth-resolution/availability on an unknown/vulnerable **Node-bundled** undici version, including unconfigured/local-only startup. Removing the deny-ambient adapter means Pi may consult host credentials during availability checks; a static-only unsafe-runtime mode is not provided. Supported fixed branches are stable `>=6.29.1 <7`, `>=7.30.1 <8`, or `>=8.12.2`; later stable majors pass this known-advisory gate, not a perpetual-security claim. Old majors and prereleases fail closed. The error includes actual Node/bundled undici versions. Inspect with `node -p "JSON.stringify(process.versions)"`. No waiver flag exists. Node 22.23.4 / bundled undici 6.29.1 is the current validated baseline; historical 22.23.2/6.28.0 is unsafe and refused. Trusted code is not sandboxed; even `allowNetwork:false` does not promise that native credential checks/commands perform no I/O.

The union of affected ranges for GHSA-4qv8-2p9j-2685, GHSA-f72v-6w45-q472, GHSA-xjj6-f33q-929c, GHSA-4w7w-5xrc-9h26, GHSA-2m5v-pch6-74hx, GHSA-qrxm-fqhp-jwvm, GHSA-9fm3-97px-rjf6 and GHSA-55wc-3pg8-jfw6 is `>=4.0.0 <6.29.1`, `>=7.0.0 <7.30.1`, `>=8.0.0 <8.12.2`. Older unsupported branches are also refused. Review newly published advisories before deployment. Residual minimatch and development findings remain documented in [development](development.md#dependency-findings); this is not an audit-clean claim.

Development: `npm run dev` admits the exact Vite origin `http://127.0.0.1:5173` and proxies with the backend Host. For another development origin explicitly set `PISPARK_DEV_ORIGIN` (literal loopback HTTP origin); set `PISPARK_API_TARGET` for Vite's backend address. No CORS grant is emitted. Production has no extra allowed origin by default. Non-browser local clients may omit Origin; browsers must obey same-origin JSON requests. Host must match the actual local listener port, or be the remote address while remote access is on (`https://` Origin, a paired device's cookie; see below). Cross-site Fetch Metadata, `Origin: null`, foreign origins/hosts, non-JSON mutations, compressed and oversized requests are rejected.

## Version 1 wire contract

Types: `apps/server/src/contract/protocol.ts`, `provider-protocol.ts` and `agent-protocol.ts`. Agent management has its [own bounded operation table](agents.md#http). Browser-independent HTTP JSON plus SSE; no arbitrary extension EventBus, tool, credential-read, resource-loading or native-file RPC.

| Endpoint | Meaning |
| --- | --- |
| `GET /api/catalog` | `{home, recentFolders}`: starting points for the New session folder picker |
| `GET /api/live` | The workspace stream (server-sent events): `ready` once it listens, then `changed {areas}` naming what changed: `sessions`, `schedules`, `routines`, `processes`, `host`. A client reads everything on `ready` and then only what changed, instead of polling. A loaded session's change is noticed within about 0.1 s, everything else within 2 s; the server reads nothing while no one listens. The stream ends after five minutes; the client follows on at once |
| `GET /api/sessions` | `{sessions, truncated, unreadable?, archived}`: the newest 256 sessions in use, and how many are archived; `?archived` lists the archived ones instead. A [child session](session-runtime.md#child-sessions) carries `parent`. A session waiting on a question carries `question`, its title's first line (at most 120 characters, without a trailing colon); a running reply carries `workingSince`, when it started |
| `POST /api/commands` | Exact typed JSON command, UUID `commandId`; HTTP 202 correlated receipt |
| `GET /api/receipts/:commandId` | Current accepted/settled receipt;404 `unknown-receipt` after expiry/restart or unknown ID |
| `GET /api/sessions/:uuid` | The session document: status, model, queue, error, what extensions show and the commands they registered (`commands: {name, description?}[]`, at most 50), and the agent's prompt templates (`prompts`, the same shape, at most 100; the reply box offers both as you type `/`); no history |
| `GET /api/sessions/:uuid/items?before=ID&limit=N` / `?after=ID` | Finalized items on Pi's active branch, oldest first, read straight from Pi's session; bounded by count and bytes; `head` is the session's last entry id, `more` says whether the page was cut |
| `GET /api/sessions/:uuid/live` | SSE: one `snapshot` of the live document, then `ops` batches (see below). A session that is not loaded answers one `unloaded` event: open it, then reconnect |
| `GET /api/sessions/:uuid/items/:id/parts/:n` | An image part's bytes, or with `?offset=` a chunk of a clipped text part |
| `GET /api/settings` / `POST /api/settings {maxRunning?, unattendedPaused?}` | PiSpark's own settings, saved in `<home>/settings.json`: how many sessions may have an agent working at once (1–32, default 8), and Pause all unattended runs ([wakes](session-runtime.md#wakes)). A change names only what changes |
| `GET /api/host` / `POST /api/host {action}` | This PiSpark: its version, address and data folder, what a restart would interrupt (`running`), and, when the launcher runs it (`managed`), its channel, automatic updates and where an update stands (`contract/host-protocol.ts`). `POST` passes `check`, `apply {when: idle|now}`, `cancel` or `configure {channel?, autoUpdate?}` to the launcher (`202`); `409 not-managed` when no launcher runs this server ([install](install.md)) |
| `GET /api/remote` / `POST /api/remote {action}` | Remote access (`contract/remote-protocol.ts`): Tailscale on this computer, the address, whether it is on, the paired devices and the current pairing code. `POST` `on`, `off`, `pair`, `cancel-pairing` or `remove {device}`, answered with the new status. From this computer only (`403` from a device) |
| `GET /api/remote/me` | What the asking browser is: `{remote: false}` on this computer, `{remote: true, device?}` at the remote address (renews a paired device's cookie) |
| `POST /api/remote/pair {code, name}` | At the remote address only: pairs a device with the current code and sets its cookie (`201 {device}`); a wrong, used or expired code is `403 invalid-code`. Every other request at the remote address without a paired device's cookie is `401 unpaired` |
| `GET /api/schedules` | `{paused, schedules}`: every [schedule](session-runtime.md#schedules), with its session's title and agent, `next`, `waiting`, `held: "archived"` and its last ten `runs` |
| `POST /api/schedules {sessionId, cron \| at, prompt, on?, run?, report?}` | Adds a schedule to a session (201); `invalid-input` for a bad time or prompt, `busy` for an archived session |
| `POST /api/schedules/:id {cron?, at?, prompt?, on?, run?, report?}` | Changes some fields; a new time, or switching on, counts from now |
| `POST /api/schedules/:id/run` / `/remove` | Run now (202; `busy` while the session works or waits) / remove |
| `POST /api/sessions/:uuid/attachments` | A file a person attaches: the raw bytes as the body, its name in `X-File-Name` (URI-encoded). Stored in the session's `files/` under a free name (`notes (2).txt`); `201 {name, size, type}`. At most 100 MB (`413`); `404` for an unknown session; `400` for a name that is not one plain file name |
| `GET /api/sessions/:uuid/attachments` | `{files: {name, size, modified, by?}[]}`: the session's `files/` folder, newest first, at most 200. These are the session's artifacts: what the person attached (`by: "you"`) and what the agent made there for them (`"agent"`, as PiSpark's guidance tells it). `by` is left out while the session isn't open |
| `GET /api/sessions/:uuid/attachments/:name` | A file of the folder, served as inert data (`nosniff`, a sandboxing CSP) |
| `POST /api/sessions/:uuid/calls` | An extension component's `host.call` (see below) |
| `GET /api/views/:hash.js` | An extension's compiled Svelte component, addressed by its content; the session document lists them under `extensions.views` ([extensions](extensions.md)) |
| `GET /api/views/assets/:hash.:ext` | A static file an extension component imported (image, font, sound, video, PDF), addressed by its content and served as inert data |
| `GET /api/sessions/:uuid/files?point&key&path` | An extension component's `host.file`: a file inside the folder its own placement named, as it is now; at most 64 MiB, not cached, served as inert data; `404` outside that folder or when the placement named none |

Commands: `create {folder?,model?,agent?}`, `open/cancel/stop/archive/restore/delete {sessionId}`, `reload {sessionId,model?}`, `rename {sessionId,title}`, `seen {sessionId}`, `configure {sessionId,model?,thinking?}`, `start/steer/follow-up {sessionId,text,attachments?}`, `answer {sessionId,dialogId,value}` (a string, a yes/no or `null` to dismiss an [extension question](extensions.md)). All require `commandId`; unknown fields are rejected. `folder` is an absolute path of an existing folder on the backend host; it is left out for a project agent, which works in its own, and refused (`invalid-input`) when given for one. It may also be left out for an [app agent](agents.md#app-agents), which then works in its own folder under the data folder. `agent` is an agent ID (Default when omitted). `configure` changes the model or thinking level between replies (after a failed one too) through Pi's own `setModel` and `setThinkingLevel`. Pi records the change in the transcript, and the session keeps it when it opens again; a thinking level the person chose goes on with a new model, clamped to what it offers, and `busy` is refused while a reply runs. The session document carries `thinking {level, levels}` and `context {tokens, window, percent}` from Pi's `getContextUsage`, with `tokens` and `percent` null right after a summary. A session whose last reply failed is started again from its transcript by the next command that needs it, so the next message goes. `reload` restarts an idle session's Pi session from its transcript so agent changes apply; `reload {sessionId, model}` also makes it run that model from now on (how a [read-only](session-runtime.md#reading-without-a-provider) session whose model is gone goes on). A read-only session (`readOnly: "model" | "agent" | "folder"`) can be read but refuses `start`, `steer`, `follow-up` and `answer` with `read-only`. A summary carries `unread` when the session did something since a person last looked at it (`seen`, sent when it is on screen in a page in view; shared by every device; a new session starts seen). Notifications: a push carries no content, so the browser's push service learns only that something happened; the service worker (`apps/web/public/sw.js`) then reads the text from `pending`. Every summary carries `lastActivity`, when the session [last did something](session-runtime.md#last-activity). `archive` unloads a session and leaves it out of the list (refused with `busy` while it runs, is queued or waits for an answer); an archived session is not opened until `restore`. `delete` removes an archived session's folder for good (`busy` when it is not archived); its working folder is not touched. Session summaries expose `folder`, `agent {id,name,layered,home?}` (`home` is an app agent's home view) and, for open sessions, `agentChanged` when the resolved agent no longer matches the one the session started with, and `waiting` while an extension's question waits for an answer. Start input may be an agent `/command`; Pi expands prompt templates as in terminal Pi. Optional `title` is bounded session content (one line, at most 80 Unicode code points). The first accepted start input of an empty, never-started session supplies a normalized fallback before dispatch; later inputs do not overwrite a present title. The native PiSpark integration tool can update it during ordinary agent execution, until a person renames the session (`rename`, as terminal Pi's `/name`): their name stays, and the agent's title tool no longer changes it; see [the session-bound capability](session-runtime.md#built-in-pispark-session-integration). There is no background naming model request or history backfill, and titles are not operational log fields. Optional `hasHistory` projects the existing host metadata fact without reading transcripts; an absent field is not evidence of an empty session. Older v1 metadata without titles remains valid. Untitled saved sessions show **Untitled session**, truly empty sessions **New session**, with dates as secondary context. Shared sidebar/header presentation observes title changes immediately. Details show only Agent, Model, Folder and Started, not UUIDs, revisions, queues or projection constants. Example:

```json
{"commandId":"e4e803d2-72f3-4b3b-855b-a64814f18e43","type":"start","sessionId":"4f964eb2-43fa-4122-8b48-c81ea576c978","text":"Read the project overview."}
```

**Attachments.** `attachments` names files uploaded to the session (at most 20, each once). Where the text places `<file name="<name>"></file>`, the server puts the attachment's absolute path, the tag terminal Pi uses for `@file`; an attachment the text does not place is added at the end. The agent opens files with its tools: nothing is pasted in. An image also goes to the model as content, resized by Pi, in the order the tags appear (Pi puts images after the text). Only tags pointing into the session's own `files/` folder are read as images; any other tag is just text. A prompt that waits for a run slot keeps its tags, so a restart loses nothing. The web shows each tag in a sent message as a chip in its place, with a thumbnail for an image.

202 means **accepted for dispatch**, not successful model execution. A receipt settles with outcome completed/cancelled/failed/queued/handled and safe error code; create supplies the new session ID when settled. Start settlement follows the real SDK completion promise. A command wait timeout does not prove that noncooperative work stopped or ownership was released. Cancellation clears queues and is cooperative, not rollback. Stop unloads with native extension cleanup; open restores history but never restarts a prompt.

An extension component's `host.call` is not a command: `POST /api/sessions/:uuid/calls {point,key,name,data?}` runs a function of the component's own placement and answers `200 {result?}`, or `200 {error:"extension",detail}` with the extension's own message (`404` for a function that placement does not have, `400` for a bad request, a timeout or a closed session). Nothing is retained once it answers, so components may call as often as they need.

Retained command IDs are deduplicated (different payload with same ID is invalid). Ordinary commands have at most 256 receipts and 16 pending; a `start` does not count toward the pending reserve, since its prompt may wait for a run slot and there is at most one per session. Cancel/stop use a separate bounded reserve of 32 receipts and 16 pending, so ordinary saturation cannot disable lifecycle controls. Concurrent controls of the same type/session coalesce to the canonical receipt returned in the202 response; poll its returned `commandId`, not the proposed duplicate ID (no unbounded alias registry). Lifecycle floods can exhaust their own reserve, not ordinary admission. All settled receipts expire10 minutes after settlement. Active receipts are not evicted. Admission fails rather than forgetting retained outcomes. Receipts are memory-only: after restart/expiry **unknown does not mean unexecuted**. Never blindly retry a side-effectful command. Inspect session/history and make a deliberate new request. Ask/reply clear only the unchanged submitted draft revision, retaining newer edits (including edits away and back). Command failures remain associated with their originating session across selection changes; connectivity/configuration notifications are explicitly workspace-wide. The UI never automatically resends commands; it reports uncertain acceptance with correlation ID. Receipt polling is separate from observation so coalescing cannot erase a run's terminal result while retained.

## Items, the live document and operations

Pi's session is the only transcript. An **item** is one entry of Pi's active branch projected for the session (`user`, `assistant`, `toolResult`, `custom`, `summary`, or an `entry` an extension renders), with Pi's own content parts: text, thinking, tool calls with their parsed `args`, and images by reference (`{mimeType, bytes}`, never inline base64). Tool results carry Pi's structured `details`, bounded. Messages carry `at`, when Pi recorded them (epoch milliseconds), and model responses `durationMs`, the time Pi measured from request to end; the web shows a turn's time from them ("Working · 12s", "Worked 1m 42s"). Ids are Pi's entry ids; `key` is stable for an item's whole life, including through its commit. Text parts over 128 KiB (and any item's text over 192 KiB) arrive clipped with their full `size` and are read in 64 KiB chunks. `args` and `details` are bounded per string (32 KiB, or 256 KiB for a top-level `patch` or `diff`), per collection, by nesting and in total (256 KiB of one message's arguments, 512 KiB of details); a cut tool call says `clipped`, and so does an item whose details were cut. An item larger than 768 KiB serialized, and an in-flight tail larger than that together, shrink further (details and arguments dropped, text kept to its first 16 KiB) and say so, so no snapshot outgrows a frame. Nothing is redacted: PiSpark never sends credentials, and what a model or tool wrote is shown as written. History is immutable, so clients page it by cursor and a reconnect needs only what the session gained.

The **live document** is `{ session, tail, progress }`: the session document, the items not yet in Pi's session (unpersisted messages and the one being written), and what running tools have reported so far. Pi reports a running tool only as `tool_execution_update` events, never in its state, so the server keeps the latest partial result per call (a reference, no work in the listener) and projects it on request as `progress[callId]`: the last 8 KiB of its text output and up to 8 KiB of details, for at most 64 calls, keyed by the same opaque id as the tool call. A call leaves `progress` when it ends; its result arrives as an item. Calls nested inside another tool are not shown. `GET …/live` sends it once as a `snapshot` (with `head`, the last entry id), then `ops` batches with consecutive `seq`. Operations are `set` a value at a path, `append` to a string, `del` a key, and `commit {after, head, items}`, which says the session gained entries (its items arrive inline unless large, in which case the client reads them as history). The server turns Pi's many small events into one batch per 50 ms by diffing the document against what that connection last saw, so a growing answer costs what it grew by. A `seq` or `after` mismatch, or any error, means the client reconnects: it receives a fresh snapshot and fetches `items?after=<its head>`. There is no replay log.

Every connection ends after 60 s so abandoned ones are freed; clients reconnect immediately and cheaply. Images are served with a fixed content type from an allow-list, `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox`; an SVG is only ever drawn as an `<img>`.

Limits: 72 KiB request body (64 KiB prompt), 5 s body read, 32 in-flight HTTP operations, 16 SSE connections total, 256 KiB for ordinary responses, 1 MiB for a live frame or an items page, 2 s blocked-write deadline, 60 s SSE lifetime with reconnect; normal executable admits 64 sockets, a 10 s header deadline and 5 minutes per request (an attachment upload). A stalled writer holds at most one serialized frame and one latest runtime invalidation, not an event backlog, and is closed if it does not drain. The pull-based browser decoder bounds incomplete frames/chunks and applies operations in order, keeps at most 32 unsent reply drafts of 65536 characters, and retries only observation after 2 s. Raw native conversation memory/disk and trusted SDK/tool allocations are not bounded by transport limits. Session listing caches host metadata across polls. Local writes update the cache immediately, external changes are reconciled every 30 seconds, and unreadable entries are counted separately from healthy sessions.

## Tests

`session-http.test.ts` runs the real SDK over HTTP: concurrency, cancel and queues, live snapshots and reconnect, cursor paging, clipped parts, the Host/Origin checks, receipts and their expiry, large histories, 10000 token events as deltas and deliberately blocked writes. Browser tests start a test-only server (`apps/server/test/fixtures/`, never imported by production code) with a temporary data folder and a deterministic signed-in provider. No test calls a real provider, so provider-specific sign-in and streaming are not covered by tests.

## Providers & models: native store and browser bridge

Model choice is independent of the agent: a new session uses the model chosen under the New session composer, else the agent's preferred model (if signed in), else the default. A session keeps its model when reopened.

`<data folder>/providers/` contains native `auth.json`, host `installation.json` (device identity), host `settings.json` (default model) and native model files. Model configuration from a `models.json` file is off by default; Pi then uses an in-memory model cache. Per-session model runtimes use no models file and an in-memory catalog with the resolved selection. No terminal Pi setup is required or read.

`ModelRuntime.create({authPath: explicitPath, modelsPath: explicitOrNull, modelsStorePath: explicitPath})` lets Pi construct and own native locked authentication/catalog persistence. The SDK root does not export AuthStorage; PiSpark supplies a path, not a private store adapter. Separate session runtimes deliberately share the auth path, not model/session/extension state. Native OAuth refresh and errors remain Pi-owned. New runtime instances observe persisted credentials; removing credentials does not revoke already-dispatched requests or upstream grants. Native environment/cloud configuration can still make a provider available after logout. `$ENV` interpolation and credential commands are trusted operator semantics; the browser cannot upload models.json, choose config paths, or request arbitrary credential resolution.

Catalog `stored` means a native stored entry exists; `source:host` means native host configuration/ambient availability without an entry, and `source:none` means unconfigured. This is coarse metadata, not an audit of which credential wins on every request (stored entries can reference env/commands). No raw native source label or secret is returned. Configured/available **does not verify account access, subscription entitlement, quota, or connectivity**.

All use the existing local Host/Origin/Fetch Metadata guard, exact JSON fields and bounded admission. Mutations return200 `{ok:true}` or400 safe `{error:code}`; catalog/start/observe return their projections. Settings bodies are limited to 16 KiB, catalog output to 2 MiB, response values to 8192 UTF-8 bytes; identity fields stay nonempty. Refresh/logout/default HTTP waits stop after 15 seconds without cancelling the admitted operation: its result can remain uncertain and ownership is retained. Inspect status rather than blindly retrying.

Sign-in capabilities never appear in URLs, session receipts, SSE/replay, logs or browser persistent storage. Polling renews a30-second lease; deadline 10 minutes; capacity 8 with 60-second terminal retention. Only bounded current prompts/events are retained, never submitted values. Dismissing cancels, including late starts. Native HTTPS authorization/device links open explicitly. Some methods need a browser/callback on the backend host; manual fallback appears only when Pi offers it.

Secrets necessarily transit browser form/request memory and the host/native store. They are **not encrypted at rest by PiSpark**. Protect storage/backups, the host OS account and loopback clients. A committed login followed by synchronization failure is `saved-sync-failed`; committed removal followed by failure is `removed-sync-failed`. Neither is rollback or proof retries are harmless. Malformed/unreadable model configuration, composition errors or failed cache restoration disable selection with sanitized `provider-configuration`. Repair host configuration/cache and refresh/restart rather than silently accepting built-in endpoints. Existing sessions keep their chosen model; defaults affect only new sessions. Actual execution still requires account/model access. Generic failure guidance never exposes provider payloads.
