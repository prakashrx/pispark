# Session runtime foundation

[VISION.md](../VISION.md) remains authoritative. Pi owns execution, tools, context, compaction, extensions and JSONL history. PiSpark owns session identity, agent resolution, admissions, observation and orderly teardown.

This is a **client-independent runtime**, owned by the local HTTP entry point. See [setup, bounded HTTP/SSE protocol and UI](session-protocol.md). There is no configuration file; each session's setup comes from its [agent](agents.md).

## Entry point and ownership

`apps/server/src/core/runtime/session-runtime.ts` exports `SessionRuntime`, configuration types and safe `RuntimeError` codes. It holds the sessions: which are loaded, the run slots, idle unloading and settings, and is the one object `http/` talks to. The work that spans sessions has its own file, each given only what it needs of the runtime (`SessionAccess`, `runtime/session-access.ts`): [child sessions](#child-sessions) (`children.ts`), [holds](#hold) (`holds.ts`), [processes](#processes) as sessions see them (`session-processes.ts`), and runs of schedules and routines in new sessions (`runs.ts`). Each loaded session is a `Session` (`runtime/session.ts`), which owns its Pi session, what its extensions show, and its lifecycle: `starting → idle ⇄ (queued →) running → cancelling → idle | error`, and from any state `stopping → stopped`. A session that can't run opens `read-only` instead (see [reading without a provider](#reading-without-a-provider)).

Construct one owner with a `RuntimeConfiguration` whose only required field is `home`, the data folder. Sessions live in `<home>/sessions`, agents in `<home>/agents`, providers in `<home>/providers`. Tests may also pass `fixedModel` (a keyless loopback provider) and `providerSettings` (extra native providers, a models file); production never sets them.

A session's setup is its agent resolved into one Pi configuration: instructions appended to Pi's system prompt, skill folders, prompt templates (`/commands`), extension files, tool switches and settings (model preference, thinking level). The switches are passed explicitly on every start and reopen, so an agent edit plus reload takes effect even when the transcript recorded an earlier tool set. Models come from Providers & models: ProviderSettings selects a native provider/model and independent session ModelRuntimes use the explicit native authPath with Pi's normal auth/refresh semantics. A changed catalog model fails closed until settings are refreshed; changed defaults never alter an active session. Trusted provider/extension code can bypass these policies; this is **not a sandbox**.

Every session gets a separate `ModelRuntime`, `SettingsManager`, `ResourceLoader`, native extension runtime/EventBus, AgentSession and SessionManager. No process environment or working-directory switching. Settings are in memory with project trust explicitly false; cache warming, install telemetry and automatic retry are off. Native compaction remains Pi-owned. Explicit tools are cwd-bound but not filesystem-confined: read/write/shell and extension code carry host OS permissions. Admit only reviewed local code/tools/workspaces.

## Runtime API

| Method | Meaning |
| --- | --- |
| `create({ folder, model?, agent? })` | Load a new session (above the backstop an idle session unloads first), check the absolute folder exists, resolve the agent (Default when omitted), choose the model, initialize/bind native extensions, return the session document. Unknown request fields are rejected. |
| `ensure(id)` | Load a session that is not loaded, or wait for one that is loading; the HTTP layer calls it before every `start`. |
| `open(id)` | Reopen a known session's native history (or an empty session) with its agent resolved now. Never accepts a session-file path. Never prompts/replays tools. |
| `reload(id, model?)` | Stop the session and open it again from its transcript, so agent changes apply; with a model, the session runs that one from now on. While it works, the reload [waits until it is free](#setup-changes). |
| `configure(id, {model?, thinking?})` | Another model or thinking level from the next reply on, through Pi's `setModel` and `setThinkingLevel`. While the session works, the change [waits until it is free](#setup-changes). |
| `list()` | Stored metadata summaries, including empty/unloaded sessions, interrupted status and `lastActivity`. |
| `session(id)` | The session document: status, model, queue, safe error and what extensions show; no history. |
| `items(id, {before?, after?, limit?})` / `image(id, itemId, part)` / `text(id, itemId, part, offset)` | Finalized items on Pi's active branch read straight from the session, bounded by count and bytes; an image's bytes; a chunk of a clipped text part. Pi's entry ids are the cursors. |
| `liveDoc(id)` | The live document: the session document, the items not yet saved (including the message being written) and what running tools reported. |
| `observeLive(id)` | A per-connection live view (the document of unpersisted items and session state, diffed into operations on each tick) plus the invalidation iterator that says when to ask it. |
| `start(id, text)` | Send a prompt to an idle session; returns `{ completion }`, which resolves to completed/cancelled/failed, not just acceptance. If a run slot is free the run starts now (the active marker is saved before execution); otherwise the session is `queued` and the prompt is saved in `session.json` until a slot frees. |
| `queue(id, text, 'steer' or 'follow-up')` | Native queued-input hooks/semantics; resolves queued/handled or rejects busy when cancelled/superseded. Only while running, one input admission in flight. |
| `cancel(id)` | A queued prompt leaves the queue. A run: prevent new inputs, clear both queues, abort/drain, clear again after outstanding input hooks. Cooperative; cannot undo tool effects. |
| `stop(id)` | Stop admissions, abort/drain, await native `session_shutdown`, flush settings, dispose, release owner. History remains. |
| `shutdown()` | Stop new sessions/inputs and drain all live sessions, including pending initialization. |

Steer and follow-up input belongs to the run it was sent to (see adaptation 3 below). Extension-originated inputs are not host RPC admissions.

**A run Pi starts by itself is a run like any other.** An extension's `pi.sendUserMessage`, or a custom message that starts a turn, makes Pi run the agent without a `start`. A host handler on Pi's `before_agent_start` adopts it: the session is saved as active and shown as `running`, it can be cancelled, it is bounded by the run deadline and it holds a run slot. Past the limit it waits for its slot there (Pi counts as busy meanwhile) and reports `queued: true`. Pi's `agent_settled` ends it. Not handled: an extension starting a run while the session's own prompt waits for a slot (`queued`), or while the session is in `error`; that run goes on as Pi started it, untracked. A stalled trusted hook retains ownership until it actually returns; deadlines still report timeout.

Start input goes through Pi's normal prompt handling: agent prompt templates expand as `/commands` and extension commands run, as in terminal Pi. Native command-context new/switch/fork/tree/reload operations throw unsupported. Resource expansion requested by extensions also throws; additional resources require host admission. Native extension hooks, tools, bus events and lifecycle remain available. No arbitrary EventBus channel is exposed to clients.

Failures use safe codes, not raw provider/extension stacks. Items and session documents never carry SDK error diagnostics or stacks. This is not a general DLP guarantee: trusted tools/extensions and model output can contain sensitive filesystem data. Native JSONL is private server-side data and may include raw provider errors; never serve it as an unauthenticated static asset.

## Loading and unloading

### Reading without a provider

Opening a session first resolves its folder, its agent and its model (signed in, still offered). When one of these can't be had for a session that was opened before, it opens **read-only** (`status: "read-only"`, `readOnly: "folder" | "agent" | "model"` in the summary and document): its history is read from Pi's transcript with `SessionManager.open`, without Pi's agent session, its extensions or a model, and nothing about it is written. Items an extension draws itself are left out; everything else shows. Sending, steering and answering are refused with `read-only`. Reloading (with a working model, for `model`) tries the full open again, and so does the next send (`ensure`), so a session whose sign-in came back carries on. A new session that can't run still fails to start.

### Last activity

A session's `lastActivity` is when it last did something: Pi writes every entry (message, tool result, notice) to the transcript as it happens, so the transcript's last write, or when it started if it has none. It is read once and kept until the catalog's next rescan (30 s); a loaded session updates it as each message ends. Opening or reading a session doesn't change it. The session list is grouped and ordered by it.

Nobody opens or stops sessions by hand. A session loads when a client shows it (`open`) or sends to it (`ensure` before `start`). A loaded session that is idle, not shown by any client, has no open question, nothing queued and no [hold](#hold) unloads after `idleUnloadMs` (15 minutes); above `maxLiveSessions` (32) the least recently used such session unloads first, and if none can, the new session loads anyway. Extensions keep their state in Pi's session, so an unloaded session comes back as it was. A client whose session was unloaded under it (its live stream sends an `unloaded` event) opens it again by itself.

## Setup changes

A change to what a session runs is applied only while the session is free (settled: nothing runs, waits for a slot, or waits for an answer). One asked for while it works waits, and its document carries `pending {model?, thinking?, reload?}` until it applies. Changes merge: the latest model and thinking win, and one staged extension revision waits at a time. They come from three places, all through `SetupChanges`:

- **The person:** `configure` (Details → Model or Thinking) and `reload` (the session ⋯ menu, the "agent changed" notice, or closing the agent editor inside the session).
- **The agent:** `pispark_session` with `{action:"reload"}` asks for a reload of its own session, for example after editing its agent; `pispark_extension apply` and `unload` stage an extension revision and ask for a reload with it.
- **An extension:** the same requests on the session's bus (`pispark:session-request` with `{action:"reload"}`).

When the session becomes free, what waited is applied before any waiting wake. Model and thinking alone go through Pi without a reload. Anything else is one reload: the session stops and opens again from its transcript with its agent resolved now, the waiting model and thinking, and the staged extension revision if there is one. If that revision fails to load, the session opens again with the previous selection. A failure is said in the session as a notice. A reload asked for from inside the session wakes it afterwards with the outcome (a wake from source `reload`, shown as a collapsed line in the conversation), so the agent carries on and verifies; the person's own changes are quiet. If the turn was stopped (or failed), what its agent or extensions asked for is dropped (a staged revision is recorded as skipped); the person's own changes still apply. Pending changes live in memory: a session that stops, or a PiSpark restart, forgets them.

PiSpark reopens the session rather than calling Pi's in-place `AgentSession.reload()`, because the agent's resolved setup (instructions, tool switches, extension paths and model) is given when the Pi session is created.

## Run slots

At most `maxRunning` sessions have an agent working at once: Background → Sessions working at once, saved in `<home>/settings.json` (1–32, default 8; `settings()` / `updateSettings()`). A changed limit applies at once: a higher one starts waiting prompts, a lower one lets running sessions finish (`runtime/run-slots.ts`). Further prompts wait in order with status `queued` and `queued: true` in the summary; the session document carries the waiting `queuedText`. A run whose extension waits for a person (an open `ctx.ui` question) gives its slot to the next session. When the question is answered or gives up, the run needs a slot to go on and goes ahead of prompts that have not started; meanwhile it reports `queued: true`. Cancelling or stopping a session that waits for a slot ends the wait at once. A waiting prompt is saved in `session.json`: an unloaded session with one reports `queued: true`, and when the session is opened again (after a restart, say) the prompt rejoins the queue, or runs at once if a slot is free; while it waits, the session document says `restored: true`. Nothing starts until the session is opened.

## Wakes

A wake is a session being asked to work by something other than the person at the keyboard (VISION §6: a schedule, an event, another session). Every source is delivered the same way (`runtime/wakes.ts`); a source decides only when it is due and what it says. Today there are three sources: the clock (schedules and routines, below), another session (a child reporting back, below) and a process the session started (it ended, or a watched line appeared). There are no count limits: what bounds unattended work is Pause all, the run slots, and that a child cannot start sessions.

- **Delivery:** paused (`unattendedPaused` in `settings.json`), nothing runs unattended. While the session is busy (running, queued, loading or waiting for an answer) or archived, the wake waits; otherwise the runtime loads the session if needed and sends the message, which takes a run slot like any prompt. A session whose last run failed starts again from its transcript first.
- **How a source waits:** `latest` (a clock): one waiting wake stands for every later one, and paused it is recorded as missed. `queue` (messages, where every one matters): each waits in order, at most 20 per source (more are recorded as missed, `full`), and paused they keep waiting. A waiting wake goes as soon as its session is free (`SessionHost.freed`); a check once a minute catches anything missed.
- **In the conversation:** before the message, the session gets a `pispark:woken` custom entry (`WOKEN_ENTRY`: the source's kind, id and label, and the due time), so the conversation can say what woke the turn.
- **Records:** `sessions/<id>/wakes.json`, beside `session.json`: waiting wakes, each source's last ten outcomes (`ran`, `failed`, `cancelled`, `missed`, with a reason: `busy`, `off`, `paused` or `full`; `started` when the run went to a new session, which the record names; `handled` when an extension took a child's report). Deleting the session deletes them; removing a source removes its own.
- **Not here:** work an extension starts in a loaded session (Pi's `sendMessage`/`sendUserMessage` with `triggerTurn`) is Pi's, adopted as a run; it is not a wake.

## Schedules

A schedule belongs to one session and wakes it (`runtime/schedules.ts`, the clock). Exactly one of `cron` (five fields: numbers, `*`, ranges, steps and lists, in the server's local time; `contract/cron.ts`) or `at` (one time, removed once its run is done). Each schedule also has its prompt and `on`. Its wakes are `latest`, labelled with the schedule in words ("Every weekday at 9:00 am · Fri 13 Nov").

- **Where each run goes:** `run: "here"` (the default), this session; or `run: "new"`, a new [child session](#child-sessions) under it each time (its agent, folder and model), titled "6:30 am run · Fri 14 Nov", which tells the owner as `report` says (default `status`). The owner's record says `started` and names the session; the session's own state says how it went. The newest 10 run sessions of a schedule stay in use; when another starts, older settled ones are archived. A session another one started cannot run schedules in new sessions.

- **Where they live:** `sessions/<id>/schedules.json`, so a schedule lives and goes with its session. While the session is archived its schedules pass their times, and nothing is caught up when it is restored. At start the runtime reads every session's file into memory.
- **Checking:** once a minute, so a run starts up to a minute after its time. Only the latest due time counts; there is never a backlog. A run that came due while PiSpark was off is sent once if it was due within a day; older ones are recorded as missed. A schedule's runs are its wakes' records.
- **Who adds them:** a person, over HTTP (`listSchedules`, `addSchedule`, `updateSchedule`, `removeSchedule`, `runSchedule`, which is refused with `busy` while the session works and ignores Pause all), or the session's own agent through the built-in `pispark_schedule` tool (below). There is no extension scheduling API. Explicit loading is not a sandbox: an extension running in a session could send the built-in tool's request itself, and the host still asks the person first.

## Routines

An agent (typically an app) can offer routines in its `agent.json`: `routines: [{id, name, cron, prompt}]`, inherited like its folder (the nearest layer's list). Each is off until the person switches it on with an ordinary agent switch, `routine:<id>` (VISION §6: unattended work is off unless a user turns it on for an agent). `runtime/routines.ts` checks them with the schedules: each run is a new top-level session of the agent (in its folder, or an app's own place), titled "‹name› · ‹day›", sent the prompt as a wake labelled "‹name› · ‹when›". Nothing is stored for the clock: when a routine last ran is read from its newest run session (`session.json` `schedule: {id: "‹agent›/‹routine›", due}`); a routine never run, or just switched on, counts from then. A run missed while PiSpark was off is caught up within a day; paused, runs are skipped. The newest 10 runs stay in use, as for schedules. HTTP: `GET /api/routines`, `POST /api/routines/:agent/:id {on}` (writes the switch into the agent), `POST /api/routines/:agent/:id/run`.

A turn can run until it finishes, is stopped, or fails. Transport, setup, shutdown, and tool-specific deadlines still apply to their respective operations.

## Child sessions

A session can hand work to another session and carry on (VISION §6: sessions "have child sessions"). A child is an ordinary session whose `session.json` names its `parent` (`runtime/children.ts`); Pi's header records it too (`parentSession`). It is listed, opened, answered, stopped and scheduled like any session, and runs whether or not anyone watches.

- **Starting one:** the built-in `pispark_session` tool (below), or an extension in the same session sending the same request on its bus (`pispark:session-request`). Either way only the session's own children. A child gets the parent's folder (or its agent's own place), the parent's agent and model unless another agent is named, an optional title, and a first message labelled as sent by the parent (a `pispark:woken` entry whose source is the parent). PiSpark does not ask the person: a child is the session's own work.
- **One level:** a child cannot start sessions. In a child the tool is not active, and a request from it is refused.
- **Reporting back:** whoever starts a child says how it tells its parent when a run ends (`report`, kept in `session.json`):
  - `result` (the default for the agent or an extension): its last answer (at most 8 KiB, else cut with a note), and any data an extension in the child set (`pispark:result {data}`, JSON up to 64 KiB), wakes the parent: source `session`, policy `queue`, labelled "‹title› · finished" (or stopped, failed). Reports wait while the parent is busy, paused or archived.
  - `notice` (opt in when starting a child): a queued wake says how the child finished and gives a `run_id`, without putting the answer in the wake message. `pispark_session read {id, run_id}` (bus: `runId`) reads that run's answer, status and data from Pi's existing transcript. Without a run ID, `read` still returns the latest answer. If the run ended before there was a transcript, the notice gives the status without a reference.
  - `status` (the default for schedule runs): a line in the parent's conversation, a Pi custom message `pispark:status` sent with `triggerTurn: false`, so the agent reads it the next time it runs. The child gets the `pispark_report` tool to raise something that needs the parent: its text wakes the parent, labelled "‹title› · raised".
  - `none`: nothing.
- **The parent's extensions see it first:** before a report or status line reaches the parent's agent, PiSpark emits `pispark:child-ended {session, title, how, mode, text, data, runId?, reply}` on the parent's bus. An extension may reply synchronously `{action: "skip"}` (it handled it: no turn, no line; the wake is recorded `handled`) or `{action: "send", text}` (what the agent gets instead).
- **Archive and delete:** archiving a parent archives its children (refused while any of them works); restoring restores them; deleting deletes them. A child can be archived alone.

Manual forks use Pi’s transcript fork operation and inherit the source session’s saved agent and model. The source appears as their parent in navigation. A fork runs, archives, and restores independently, without sending completion reports to the source.

## Hold

An extension with live work of its own (a bot's connection, a watcher) asks to keep its session loaded while no one watches (`runtime/holds.ts`): `pi.events.emit("pispark:hold", {extension, hold: true, reason, reply})`, or `hold: false` to let go. The host grants it only if the session's agent switches `hold:<extension>` on and the session loads that extension; otherwise the session shows the request (`holdAsked` in the session document) and the person answers with the `allow-hold` (which writes the switch into the agent) or `deny-hold` command. A held session (`held: {extension, reason}` in `session.json` and the summary) is not unloaded for being idle or by the backstop, and is loaded again after a restart, so the extension's `session_start` starts its work again. Pause all unloads held sessions (their `session_shutdown` stops the work) and loads them again when it ends. The hold ends with `release-hold`, the extension's own `hold: false`, archive, delete, or the agent no longer allowing it. The extension's own runs are adopted as any (run slot, Stop).

## Processes

Commands a session runs in the background (`runtime/processes.ts` runs them; `runtime/session-processes.ts` answers the tool and tells sessions), owned by the host so they keep running while the session unloads. They run in the shell Pi's bash tool uses (`getShellConfig`: Git Bash on Windows, else bash or sh), in the session's folder unless another is given, as their own process group, with this server's permissions. Output goes to `sessions/<id>/processes/<pid>.log` (the newest 2 MB; older output is cut), the list to `sessions/<id>/processes.json`.

- **The agent:** the built-in `pispark_process` tool (below), or an extension sending the same request on its bus (`pispark:process-request`): `start {command, folder?, title?, report?, stopAfterSeconds?}`, `list`, `output {id}` (what this session has not read yet), `watch {id, pattern, report?}` / `unwatch`, `stop {id}`. `start` and `output` can wait for a regular expression in the output, and a wait always has a time limit (`waitFor` with `timeoutSeconds`). A session reaches its own processes and its children's.
- **Targeted evidence:** `wait {id, timeout_seconds}` (bus: `timeoutSeconds`) returns the process status and exit code when available, without reading output. `search {id, query}` finds a literal string, case-insensitively, in the retained log. It returns up to five matching lines with adjacent context and says if older output was discarded. Neither action consumes unread output. Use `report: "none"` on `start` if waiting explicitly and no completion wake is wanted.
- **When one ends:** its session is told in its mode (`result`, the default: the exit code and the last 4 KiB of output wake it, source `process`; `status`: a line; `none`: nothing). The conversation shows a process report as one expandable row with its source label and the recorded output inside. A watch wakes the session when a line matches, at most once a minute. Stopped by the agent, nothing is said; stopped by the person, the session is told.
- **Lifetime:** Stop ends the process and everything it started (`taskkill /T` on Windows, its process group elsewhere). Archiving or deleting the session stops its processes. When PiSpark stops, every process is stopped; after the next start each session is told "ended when PiSpark stopped". Pause all does not stop processes: they are not agent runs.
- **HTTP:** `GET /api/processes` (every running one), `GET /api/sessions/:id/processes`, `GET /api/sessions/:id/processes/:pid/output?since=N` (output after a byte offset, and where it ends), `POST /api/sessions/:id/processes/:pid/stop`. Clients read output about once a second while it is shown; nothing is pushed yet.

## Observation and limits

Observers pull invalidations; SDK listeners never invoke subscribers, perform disk I/O, or copy/serialize transcripts. This matters because Pi emits `message_end` before native persistence. A slow observer retains **one latest invalidation**, not a growing token-event queue. Re-read the live document to render the complete current state, including partial output. Sequence gaps mean coalescing, not lost durable conversation. Sequence numbers are scoped to one live owner, not durable replay cursors; reopening/restarting begins a new observation lifetime. Closing an observer does not stop the session. Creating the live view and registering its subscription is synchronous and has no interleaving gap.

Defaults: 8 sessions running at once (a setting), idle sessions unloaded after 15 minutes, a backstop of 32 loaded sessions above which idle ones unload early (never a refusal), 16 observers per session, 8 pending native inputs, 64 KiB UTF-8 input, 32 exact files per resource category, 64 MiB maximum native file on open, 10-second operation/cleanup wait, 5-minute cooperative run deadline. Live-session and deadline limits are trusted host options. History has no disk quota or retention manager. The live document and items are bounded by the projection (see [protocol](session-protocol.md)).

Deadlines do not kill arbitrary JavaScript or tools. If an extension ignores cancellation or shutdown hangs, the operation reports timeout and **retains ownership/admission** until actual cleanup completes. CPU-blocking trusted code can stall every same-process session. Strong adversarial isolation would require another approved design. A session with execution/storage error rejects new starts; inspect it, stop and reopen deliberately rather than automatically retry side effects.

## Persistence and recovery

Each session owns `<home>/sessions/<id>/`: a small `session.json` (working folder, agent ID, model, created time, optional title, active/interruption markers and the setup fingerprint), Pi's native JSONL transcript, `files/` with uploads and generated artifacts, `uploads/` recording which names came from uploads (see [protocol](session-protocol.md)), and an optional `agent/` folder once the agent is edited inside the session. The session ID is the folder name. Agents are read live: nothing is copied into the session. When any agent changes, open sessions compare a fingerprint of their resolved setup with the one recorded at start and report `agentChanged`; reload applies it. Setup-only sessions keep `session.json` because Pi does not write JSONL until the first message.

The host marks activity before model/tool execution. On reopen, unfinished activity is reported as interrupted; native finalized messages/context are restored without resuming an old request. Tokens and queues are not durable. A crash may lose partial assistant/tool output; a tool side effect may have happened without a finalized result. **No exactly-once guarantee and no automatic replay.** User-driven continuation is a new request and can perform new effects. Extension startup runs normally on reopen, so trusted extensions must reconstruct state without repeating side effects themselves.

One server per data folder is enforced by `<home>/pispark.lock`; a lock whose process is gone is replaced. Within the server, a session has at most one live owner. Local single-host storage only: no NFS/distributed locking guarantee. Symlink session directories/history files are refused. Native files with missing expected history, bad header/JSON or an unsupported format fail closed instead of silently starting a new session. Corrupt trailing bytes are not automatically repaired. Neither host metadata nor native history promises fsync/power-loss atomicity.

## Explicit Pi compatibility adaptations

Pinned `@earendil-works/pi-coding-agent` and `pi-ai` **1.5.2** require Node **22.23.4+** on the supported 22 branch (other supported majors also undergo the bundled-undici gate). The integration uses the following compatibility adaptations.

1. The package root exports ambient extension discovery, but not its explicit loader. Resolve the installed package entry, verify version 1.5.2/function shape, and call its native internal `loadExtensions` with the exact extension paths the agent resolves to and the real cwd. No copied loader and no ambient fallback. No project/home resource discovery, with one exception an agent asks for: a [project agent](agents.md#project-agents)'s session reads its folder's context files (`AGENTS.md`) with Pi's exported `loadProjectContextFiles`, given the session's own Pi folder (`sessions/<id>/pi`).
2. **Cancelling while Pi prepares a run.** Pi 1.5 sets its abort flag when `abort()` arrives during preparation (input hooks, auth, compaction, `before_agent_start`), but still calls the provider once. An instance-local wrapper on the owned runtime's public `stream`/`streamSimple` chains the request's `transformHeaders`: it awaits the SDK/extension transform, checks whether the run was cancelled or the session is stopping, and refuses the request with an AbortError (handled by native ModelRuntime's lazy stream) before anything is sent. It survives provider recomposition, adds no private import and keeps all other options and the signal. Once a run is cancelled, a provider error (including the one Pi records for a run aborted before it started) is reported as the cancel's result, not a failure.
3. **Steer and follow-up near settlement.** Pi runs a queued input's hooks asynchronously, so it can land after the run settled and wait in the queue for an unrelated next prompt. A host-owned last `input` handler refuses input whose run is no longer admitting it, and an `agent_before_settle` handler closes admission and waits for input the run already admitted, so Pi delivers it in that run. Cancelled preparation rejects explicitly without appending or deleting unrelated entries.

These do not undo prior effects or stop already executing trusted hooks from performing their own effects. Already dispatched work keeps native cooperative signal semantics.

Provider auth and selection use Pi’s public ModelRuntime and login, logout, refresh and status APIs. Pi constructs credential storage from `authPath`. In 1.5.2 Pi selects a persistent catalog only when a model configuration file is enabled. The pinned SDK boundary supplies Pi’s own `FileModelsStore` through the public `modelsStore` option when configuration files are disabled. Settings and session runtimes therefore share the refreshed catalog on disk while keeping their provider instances independent. The public stream-method wrapper above is an explicit owned-instance adaptation, not a claim of zero adaptation. Trusted extensions can still replace methods or issue their own requests; this is not isolation from backend code.

Extensions get Pi's `rpc` mode with a real UI context; see [extensions](extensions.md). An upstream explicit-loader export would remove the debt; Pi honouring an abort that arrives during run preparation would remove adaptation 2. SDK upgrades require revisiting the adapter and real-extension tests; do not silently loosen isolation to follow upstream defaults.

## Built-in PiSpark session integration

**What every session is told.** Whatever its agent, the built-in extension adds a short paragraph to the system prompt (`pisparkContext` in `core/extensions/pispark.ts`):
- it runs in PiSpark, a web workspace that the person often reads on a phone;
- files made for the person go in the session's `files/` folder, with the path given, and project changes stay in the project;
- the data folder's path;
- which built-in skills say more.

**PiSpark's own skills.** `apps/server/skills/pispark` covers presenting work and PiSpark's tools; `apps/server/skills/pispark-extensions` covers extensions with their own web components, where they live and how they load. They come in Pi's own skill format and are given to every session before the agent's own (`BUILT_IN_SKILLS`). Pi lists them by name and description, and the agent reads one when it is relevant. They are part of the system:
- the agent editor doesn't list them;
- an agent's switches don't turn them off;
- a release ships them beside the server's build.


Every created/reopened hosted session, with or without an agent, loads `src/core/extensions/pispark.ts` first through the existing explicit native module loader (source `.ts`, compiled `.js`). It is an ordinary Pi extension, not an agent resource, title-only framework or terminal installation. An agent extension that registers a tool of the same name as one of this extension's (`pispark_set_title`, `pispark_schedule`, `pispark_session`, `pispark_process`, `pispark_report`) fails session setup instead of silently shadowing it.

The native tool accepts only `title:string`; its guidance asks for a short title in the first reply once the purpose is clear, changed only when the topic meaningfully changes. A person's rename wins: `session.json` records `renamed`, and later title changes from the agent are ignored. A structured `before_agent_start` addition preserves existing prompts and advertises guidance only while the tool is active. The agent's tool switches apply to PiSpark's own tools like any other, the title tool included, on every start and reopen. Trusted extensions can subsequently change tools/prompts; there is no forced-tool policy or sandbox.

The tool names the session with Pi's own `pi.setSessionName`, so there is no PiSpark-specific channel: Pi records the name in the transcript and emits `session_info_changed`, and the runtime saves that name as the session title. Any extension's `pi.setSessionName` renames the session the same way.

Its second tool, `pispark_schedule`, lists, removes or adds schedules of its own session only: once (`in_minutes` or a local `at`) or repeating (`cron`). The tool sends the request to the host on the session's event bus (`pispark:schedule-request`). The host asks the person with Pi's own confirm dialog ("Schedule this in this session?", with the schedule in words and its prompt) and adds the schedule only on yes. While the tool is active, the system prompt gets one line of guidance with the server's local time and offset. An agent can switch the tool off.

Its third tool, `pispark_session`, starts, lists, sends to, stops and reads the session's own [child sessions](#child-sessions), each with how it reports; `inspect` describes the calling session and `reload` asks for its [reload](#setup-changes) when the turn ends. While it is active the system prompt says that work which can run on its own may be handed to another session, and that a report arriving while others still run needs only a one-line acknowledgement. `pispark_report` is active only in a child in status mode; the system prompt then says to raise what the parent needs to know and otherwise just finish.

Its `pispark_process` tool runs commands in the background ([processes](#processes)); while it is active the system prompt says to use it instead of bash for commands that run long or never end on their own, and to rely on the end-of-process wake or a blocking wait rather than checking output repeatedly.

The agent's tool switches go to Pi in its own terms, not as an allowlist: tools switched off are `excludeTools` (never registered, so no transcript brings them back), and tools switched on are `+name` modifiers applied on top of the loadout a reopened transcript recorded. A tool an extension registers once the session runs (in `session_start`, say) is offered like any other. Tools a running session has that loading the agent did not show are remembered for the agent editor (`ToolDiscovery.remember`).

Titles are bounded to 4096 UTF-16 units of input, normalized to one printable line and capped at 80 Unicode code points; an empty or unprintable title is a tool error. The runtime writes the title to `session.json` before showing it; a closing or cancelled session keeps its current title, and a failed save leaves the title unchanged and says so in the session. Operational logs omit titles and arguments; native tool arguments naturally remain in that session's Pi history. No historical scan, migration, separate paid naming pass or guarantee that every model invokes the tool is implied.

## Tests

`apps/server/test/session-runtime.test.ts` uses the real pinned SDK with a deterministic in-process provider, ordinary extension files and real tools: simultaneous sessions, in-flight output, cancel and queue races, extension lifecycle failures, ownership, a process killed after a tool result (no replay), resource and auth isolation, storage failures and timeouts. No test calls a real provider.

## Native provider settings ownership

Provider settings live in `<home>/providers`, covered by the data folder lock. They supply explicit auth and model-cache paths to Pi, validates native `getError()` and refresh outcomes, and fails model admission on configuration/composition/cache errors rather than silently accepting built-in endpoints. Errors returned to clients are sanitized codes. An explicit models file must be readable; malformed configuration fails startup/refresh. A failed refresh disables new selection until a successful repair/refresh or restart. Existing sessions retain their chosen model; changed defaults apply only to new catalog-enabled sessions. Removed/unavailable saved defaults stay visible, never silently replaced.

Shutdown stops settings admission first and drains admitted default writes, refresh and logout before shutting down. HTTP waits are bounded to 15 seconds but a timeout does not cancel or prove failure of the operation; inspect status before retrying. Noncooperative native work can keep shutdown waiting indefinitely. Session shutdown starts independently, even if provider cleanup fails or hangs. Auth cancellation uses Pi's native abort semantics: it may stop waiting while trusted provider code continues; native locks/signals guard credential persistence, not arbitrary hook side effects. A credential can be committed before synchronization fails; login/logout report that partial outcome, never serialize its credential/cause. No forced teardown or rollback is claimed.
